# V2 Implementation Plan: Excel-Only Performance Path (Target P95 <= 2s)

## 1. Goal
Build V2 so the platform keeps real Excel calculation at runtime while improving performance to practical production levels.

Primary target:
- P50: 1.0s to 1.5s
- P95: <= 2.0s for standard raters
- P99: track and reduce, expected to remain above 2s for very heavy models initially

Non-goal:
- Hard guarantee of sub-1s for all complex workbooks.

---

## 2. Why this V2 path
This path preserves the current product value:
- Excel remains source of truth and runtime authority.
- No LLM dependency in core premium calculation.
- Better auditability and deterministic behavior.

Tradeoff accepted:
- Performance is optimized aggressively, but still bounded by workbook complexity.

---

## 3. Current bottlenecks (V1)
The major latency contributors are:
1. Per-request calc process overhead.
2. Workbook copy/load/save/read I/O on each call.
3. Full recalc on large dependency graphs.
4. Single-threaded/limited worker throughput under concurrency.

---

## 4. V2 Architecture
## 4.1 Request flow
1. API receives request.
2. Request is routed to a warm calc worker from a pool.
3. Worker uses isolated session file in fast local temp storage.
4. Inputs are written.
5. Recalc executed by warm engine process.
6. Outputs read and returned.
7. Session artifacts cleaned up.

## 4.2 Core components
1. API gateway layer:
- FastAPI endpoints remain stable.
- Adds queue/worker orchestration.

2. Worker pool manager:
- Fixed-size pool per app instance (start with 2 to 4 workers).
- Health checks and worker recycle policy.

3. Session storage layer:
- Local SSD temp path.
- No network drive temp usage.

4. Optional result cache:
- Key: (rater_slug + normalized_input_payload_hash).
- TTL-based invalidation.
- Bypass cache for explicitly uncached scenarios.

5. Telemetry layer:
- Stage-level timings and percentile dashboards.

---

## 5. Implementation details
## 5.1 Backend changes
1. Add a worker-pool coordinator module:
- Acquire/release worker.
- Timeout and retry policy.
- Backpressure when pool is saturated.

2. Update engine path:
- Minimize file open/save cycles.
- Write only required/changed cells.
- Keep strict isolation per request.

3. Add structured performance metrics for each request:
- copy_ms
- write_ms
- calc_ms
- read_ms
- total_ms
- cache_hit (true/false)
- rater_slug

4. Add request id tracing:
- Correlate API logs with worker-stage timings.

## 5.2 Caching strategy
1. Use cache only for identical payloads.
2. Normalize payload before hash:
- sort keys
- trim strings
- canonical number formatting

3. Cache TTL recommendations:
- 5 to 30 minutes for quote-like traffic.
- disable cache for test/debug modes.

## 5.3 Concurrency and resource control
1. Pool size based on CPU cores:
- baseline: min(cores, 4)

2. Hard guardrails:
- max queue depth
- worker timeout (for example 8s to 15s)
- circuit breaker when worker failures spike

3. Graceful degradation:
- return clear busy response if queue full
- avoid unbounded memory growth

---

## 6. Azure deployment and DevOps optimizations
## 6.1 Hosting recommendations
1. Use compute with adequate CPU for calc workloads.
2. Enable always-on behavior (avoid cold starts).
3. Use local ephemeral disk for temp sessions.
4. Separate API scale from worker density tuning.

## 6.2 Container/runtime settings
1. Pre-warm worker pool during startup.
2. Health endpoint should validate worker availability.
3. Pin process limits to avoid CPU starvation.

## 6.3 CI/CD pipeline additions
1. Pre-deploy smoke tests:
- config load test
- one calculation per major rater

2. Post-deploy performance canary:
- run benchmark bundle
- compare against baseline thresholds

3. Release gate:
- fail promotion if P95 regression exceeds threshold.

---

## 7. Performance test plan
## 7.1 Dataset
1. At least 3 raters:
- light model
- medium model
- heavy model

2. At least 200 to 1000 requests per rater profile.
3. Mix of repeated and unique payloads.

## 7.2 Metrics to report
1. P50/P95/P99 latency.
2. Throughput (req/s).
3. Error rate.
4. Stage timing breakdown (copy/write/calc/read).
5. Cache hit ratio.

## 7.3 Acceptance criteria for V2
1. P95 <= 2.0s for light and medium raters under agreed load.
2. No regression in output parity vs baseline Excel outputs.
3. Error rate below agreed threshold (for example <0.1%).

---

## 8. Rollout plan
## Phase 1: Observability first
1. Add stage timing logs and dashboards.
2. Measure current baseline by rater.

## Phase 2: Worker pool + warm path
1. Introduce pool manager.
2. Enable warm worker execution.
3. Validate parity and stability.

## Phase 3: Cache + infra tuning
1. Add cache for duplicate payloads.
2. Tune compute, temp storage, and pool size.

## Phase 4: Controlled production rollout
1. Canary traffic.
2. Compare percentile metrics vs baseline.
3. Full rollout after stable window.

---

## 9. Risks and mitigations
1. Risk: Worker leaks or stuck sessions.
- Mitigation: timeout + recycle policy + health checks.

2. Risk: Cache returns stale or mismatched result.
- Mitigation: strong key normalization + TTL + disable switch.

3. Risk: Heavy workbook still above target.
- Mitigation: workbook-level optimization plus rater-specific SLA class.

4. Risk: Concurrency spikes degrade all requests.
- Mitigation: queue caps, backpressure, autoscale rules.

---

## 10. Team responsibilities
1. Backend team:
- worker pool, engine path tuning, telemetry.

2. Model team:
- identify heavy formulas and optimize workbook structures.

3. DevOps team:
- infra sizing, warm startup, release gates, dashboards.

4. QA team:
- parity test suites and percentile performance validation.

---

## 11. Final recommendation
Adopt this V2 Excel-only optimization path as the primary production roadmap.

Reason:
- Preserves the product's core value (real Excel runtime).
- Avoids LLM dependence in core calculation.
- Delivers meaningful performance gains with controlled risk.
- Provides a strong governance story for enterprise adoption.

## 15. Where we can go wrong (risk register)
1. Risk: API response shape changes during migration.
- Mitigation: snapshot contracts, block breaking changes.

2. Risk: Schedule mode behavior mismatch between old JS and Next.js implementation.
- Mitigation: extract current behavior into explicit test cases before migration.

3. Risk: Numeric coercion differences (string vs number).
- Mitigation: strict type normalization in one shared serializer module.

4. Risk: Download flow breaks due to blob handling differences.
- Mitigation: dedicated integration tests for download endpoints.

5. Risk: CORS/dev proxy misconfiguration.
- Mitigation: explicit dev proxy config and environment docs.

6. Risk: CSS regressions on smaller screens.
- Mitigation: visual checks at defined breakpoints (mobile/tablet/desktop).

7. Risk: Team merges large PRs causing unstable branch.
- Mitigation: phase-based small PRs, each with test gates.

Migrate to Next.js now only if team capacity supports the full phase plan and testing gates.
